# Trois concepts Studio Phantom (2026-11-26)

Choisis dans le classement `data/idees/2026-11-26.json` (11 idées notées /100 par `npm run fm -- idees`). Chaque fait ci-dessous vient d'une
source ouverte aujourd'hui (`fm repo` et README/`SKILL.md` lus). **Aucun épisode n'est produit, rien n'est publié.** « À réaliser » = démonstration
que personne n'a encore faite : tant qu'elle ne l'est pas, la vidéo dit ce que dit la source, jamais « j'ai testé ».

## 1. Claude Code business : audits de page de conversion (catégorie B, 76,5/100)
**Source :** skill `cro` du dépôt `coreyhaines31/marketingskills` (MIT, plus de 62 000 étoiles, actif le 26/11/2026). Description de la skill, mot pour mot :
« When the user wants more conversions from a page or form, or asks why a page isn't converting, what to change first, or whether to add or remove a field or element: landing and pricing pages, lead forms, or a URL shared for feedback. »
**Hook retenu (90/100)** : « Arrête de scroller, car maintenant, avec Claude Code, tu peux auditer une page de vente en quelques minutes. »
Autres : « Ta page ne convertit pas ? Ce skill Claude Code dit quoi changer en premier. » (87) · « Freelance ? Voici une prestation d'audit de page que Claude Code prépare pour toi. » (87) · « …tu sais quoi changer en premier sur une page qui ne vend pas. » (80) · « Avant, un audit prenait une demi-journée… » (70, « demi-journée » non sourcé : rejeté).
**Script (≈ 100 mots, à produire après la démonstration)** — Ouverture. « Tu donnes l'adresse d'une page à Claude Code. Le skill *cro* lit la page et classe quoi changer en premier. Ce que Claude fait seul : repérer les blocages et proposer des textes. Ce qui reste humain : décider, tester, parler au client. Coût : le skill est gratuit (MIT) ; il te faut un accès à Claude Code. Limite : un audit n'est pas une promesse de ventes. Dis-moi en commentaire : quelle page tu ferais auditer ? »
**Démonstration visuelle (à réaliser)** : écran réel, une page de démonstration publique → commande dans Claude Code → liste « à changer en premier » qui s'affiche → avant/après du titre. Utiliser une page à nous (jamais le site d'un tiers sans accord).
**Potentiel** : utilité 9, sauvegarde 9 (checklist), démonstration 8 ; le business reste honnête (prestation ≠ revenu promis). Risque : sujet proche de la vidéo « audits SEO » du 18/11 (même dépôt) : angle différent (conversion, pas SEO), à signaler dans le script.

## 2. Automatisation IA impressionnante : un reviewer de code qui commente ligne par ligne (catégorie D, 78/100)
**Source :** `alibaba/open-code-review` (Apache-2.0, plus de 56 000 étoiles, poussé le 26/11/2026). Description, mot pour mot :
« Secure, fast, efficient, battle-tested at Alibaba's scale. Hybrid architecture code review tool: deterministic pipelines + LLM Agent, precise line-level comments, built-in multi-language ruleset (NPE, thread-safety, XSS, SQL injection), OpenAI & Anthropic compatible. »
**Hook retenu (90/100)** : « Arrête de scroller, car maintenant, avec Claude, tu peux faire relire ton code ligne par ligne par un reviewer automatique. » (« avec Claude » : la description dit compatible Anthropic ; à confirmer dans le README avant d'écrire.)
Autres : « Tes pull requests attendent une relecture ? Cet outil commente déjà chaque ligne. » (87) · « …un reviewer automatique repère des failles XSS et SQL injection… » (80) · deux autres < 60.
**Script (≈ 110 mots, à produire après lecture du README et un essai)** — Ouverture. « C'est un outil de revue de code qui mélange des règles fixes et un agent. Les règles repèrent les cas connus (valeur nulle, concurrence, XSS, injection SQL) ; l'agent commente à la ligne près. Automatisable : la première relecture. Humain : décider de fusionner. Coût : l'outil est gratuit (Apache-2.0), le modèle que tu branches ne l'est pas. Limite : un reviewer ne remplace pas une relecture humaine. Dis-moi : sur quel projet tu l'essaierais ? »
**Démonstration visuelle (à réaliser)** : un petit dépôt de test volontairement faillible → l'outil lance → les commentaires apparaissent sur les lignes → capture réelle. Si l'essai échoue, on le dit ; on n'invente aucun résultat.
**Potentiel** : curiosité 8, démonstration 8, partage 7 (développeurs). Point faible : public technique ; garder un seul chiffre (étoiles) et un exemple de faille.

## 3. Skill GitHub puissant : « penser comme le dev le plus paresseux » (catégories E + G, 82 et 83/100)
**Source :** `DietrichGebert/ponytail` (MIT, plus de 199 000 étoiles, actif il y a 5 jours). Description, mot pour mot :
« Makes your AI agent think like the laziest senior dev in the room. The best code is the code you never wrote. »
« Méconnu » n'est **pas** établi (beaucoup d'étoiles) : le sujet est inédit **pour la chaîne** et pour le public francophone, pas pour GitHub.
**Hook retenu (90/100, avec réserve)** : « Arrête de scroller, car maintenant, avec Claude Code, tu peux demander moins de code pour le même résultat. » — « pour le même résultat » n'est **pas prouvé par la source** : il ne peut servir qu'**après** l'expérience. Sans expérience : « …ton agent peut penser comme le dev le plus paresseux de l'équipe. » (78, 100 % sourcé).
**Script (≈ 100 mots, version expérience)** — Ouverture. « J'ai donné la même tâche à Claude Code, une fois sans le skill, une fois avec. Voici les deux codes, côte à côte : [nombre de lignes mesuré]. Ce que fait le skill : il pousse l'agent à écrire moins. Ce qu'il ne fait pas : garantir que le code est meilleur. Limite : un seul essai ne prouve rien. Dis-moi : quelle tâche tu veux que je compare ? » (Les chiffres sont mesurés, jamais écrits d'avance.)
**Démonstration visuelle (à réaliser)** : écran partagé, même consigne, deux sorties, compteur de lignes qui s'incrémente, test qui passe/échoue. C'est l'idée la plus forte du lot (G, 83) : la démonstration *est* la vidéo.
**Potentiel** : curiosité 9, démonstration 10, partage 8. Condition : réaliser l'expérience pour de vrai (et la refaire sur 3 tâches avant de conclure quoi que ce soit).

## Ordre conseillé
1. **Ponytail (expérience)** : meilleur potentiel, démonstration-first ; 2. **Reviewer de code** ; 3. **Audit de conversion**.
Les trois ont une catégorie différente (G/E, D, B) et passent les règles de preuve ; aucun ne présente une ancienne fonction comme nouvelle.
